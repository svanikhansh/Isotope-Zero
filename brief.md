# isotope_zero — Complete Project Brief

A single-file, exhaustive reference for the isotope_zero project: every module,
prototype, integration, adapter, release, and design decision. Local-first,
NumPy/BLAS-accelerated cognitive memory for AI agents. (The shipped Rust native
extension was removed in v1.3.0 — the wheel is pure-Python; see the v1.3.0
superseding markers throughout.)

## 1. What it is (one-paragraph elevator pitch)

isotope_zero is a sub-millisecond, local-first cognitive memory layer for AI agents. It compresses a multi-turn conversation's worth of facts into a SQLite-backed store of memory cards, each carrying a fact, minimal evidence, a 384-dim L2-normalized embedding, and an Ebbinghaus retention state. On recall, a hybrid router fuses semantic cosine similarity, FTS5 BM25 lexical search, and a semantic knowledge-graph boost via Reciprocal Rank Fusion, reweighted by temporal decay so recently recalled facts surface higher. Everything runs in-process with zero network calls — embeddings come from a quantized local ONNX MiniLM served by an optional shared-memory daemon, vector scans ride platform BLAS (Accelerate on macOS) at sub-0.3 ms p99 for 10k cards, and the whole package hard-depends only on numpy. It ships as a pure-Python pip-installable package (v1.3.0 removed the Rust native core — the wheel is NumPy/BLAS-accelerated, no compiled extension) with an MCP stdio server, a 15-command CLI, editor plugins for Claude Code/Cursor/Codex, framework adapters for LangChain/LlamaIndex/AutoGen/CrewAI, and an npm launcher for JS-first environments.

## 2. The thesis & design principles (local-first, efficiency-first, cognitive)

The thesis: an AI agent's memory should be local-first, efficiency-first, and cognitive — modeled on how human memory actually works, rather than on a cloud API that happens to store text. Six principles flow from this.

**1. Local-first, zero-network.** No embedding API, no hosted vector DB, no auth token. Memory persists in SQLite at `~/.isotope_zero/` and is never transmitted. The offline guarantee is enforced at import time: `grep -rnE '^\s*(import|from)\s+(requests|urllib|httpx|aiohttp|openai|http)'` over `src/isotope_zero/integrations/` returns nothing. No `url`, no `Authorization`, no `api_key` field appears in any manifest. This is the headline differentiator against mem0, and it is structural, not a config toggle.

**2. Efficiency-first: cost is a first-class metric.** Every fact is compressed into a card (fact + minimal evidence, never the full raw input), and every recall is budget-truncated by marginal token value so the agent context stays flat regardless of write volume. `tokens_saved_vs_raw` is tracked on every query. Local ONNX embeddings are `$0` inference; the benchmark measures savings against OpenAI `text-embedding-3-small` at `$0.02/1M` tokens. The single source of truth for token math is `tokens.py:estimate_tokens`, a sub-millisecond regex+char-blend estimator that every token-counting call site routes through.

**3. Cognitive: memory decays like memory.** Facts carry an Ebbinghaus retention state (`stability` default `1.0`, `importance`, `last_access`) and a semantic graph of weighted edges. Retrieval fuses 70% cosine + 30% retention (`alpha=0.70`) so a fact learned 3 seconds ago outranks a semantically similar one learned 30 days ago, all else equal. A background consolidator dedups cosine clusters, prunes stale never-recalled cards (`retention < 0.15` AND `access_count == 0` AND past grace), and merges tight graph clusters (N≥3, edge weight >0.80) into summary survivors — keeping the store flat in context size and sub-ms latency regardless of write volume.

**4. Honest measurement.** Every acceleration hypothesis was tested in a prototype and judged by measured numbers, not claims. Of six acceleration hypotheses: three were refuted (hybrid pre-filtering, mmap storage, binary POPCNT), two were partial/conditional wins (int8 quantization, native SIMD), and one was the structural-RSS daemon. The shipped product includes exactly the layers that survived measurement and defaults off the one that didn't (mmap SIGILL-crashes under 10-thread concurrency). The adversarial harness states this verbatim: **"measure reality, never fabricate a passing threshold."**

**5. Graceful degradation, never fail.** v1.3.0 ships a pure-Python wheel — there is no Rust `.so` to go missing. A missing `onnxruntime`, a dead daemon socket, or absent FTS5 never break the package: every transport fault silently degrades to a deterministic feature-hash embedding that still returns a 384-dim L2-normalized vector (identical texts score cosine 1.0, unrelated ~0), and FTS5 absence degrades hybrid search to vector-only. The hard dependency set is exactly `numpy>=1.24.0`; `sqlite3` is stdlib. `HAVE_NATIVE` is a constant `False` kept for API stability (see §4.1).

**6. One contract, parallel-built subsystems.** `types.py` freezes one dataclass contract (`MemoryCard`, `ActionType`/`ActionResult`, `QueryHit`/`QueryResult`, `ConsolidationReport`) that every subsystem depends on, so embeddings, triage, store, router, mcp, and eval were built and tested in parallel without reconciliation. `now_ts() -> float` wraps `time.time()` so tests and the benchmark monkeypatch determinism without touching `time.time` globally.

│  Foundation: Python 3.10+ · numpy/BLAS · sqlite3 (stdlib)     │

The store is the foundation: one `sqlite3.Connection` (WAL, autocommit), one `threading.Lock`, float32 embedding BLOBs packed via `array('f')`. Above it sit the retrieval and embedding kernels — vector search is one batched `matrix @ q` matmul into platform BLAS, hybrid search adds an FTS5 BM25 branch and an entity-graph boost fused by Reciprocal Rank Fusion. The cognition layer adds Ebbinghaus temporal decay, a semantic knowledge graph, and an off-hot-path consolidator. The facade hides all of this behind four verbs. Adapters and integrations sit at the top, routing every capture pipe into the local SQLite store — no network, no API key.

The throughline of the 11-phase research arc: six acceleration hypotheses were tested honestly, three were refuted (hybrid, mmap, binary POPCNT), two were partial/conditional wins (quantization, native SIMD), one was the structural-RSS daemon — and the capstone shipped exactly the layers that survived measurement.

## 4. The Python package — src/isotope_zero/ (module-by-module)

The core layer depends on one frozen dataclass contract (detailed in §4.7): `types.py` defines `MemoryCard`, `ActionType`/`ActionResult`, `QueryHit`/`QueryResult`, and `ConsolidationReport`, imported by every subsystem so parallel-built modules slot together without reconciliation.

### 4.1 core/ — store, decay, consolidation, history, mmap, native bridge, async

#### core/store.py — the persistent SQLite store (the heart)

`MemoryStore` is the stdlib-first persistent store for `MemoryCard` objects: `sqlite3` + `array` + `json` + `threading`, with numpy as an optional accelerator. It holds ONE persistent `sqlite3.Connection` (opened `check_same_thread=False`, `isolation_level=None` autocommit) for the whole store lifetime — essential for `:memory:` DBs whose data is tied to a single connection's lifetime — and serializes all DB work through a `threading.Lock`. The `memories` table (columns: `id TEXT PRIMARY KEY, fact, evidence, timestamp, tags` as JSON, `source_tokens`, `embedding BLOB`, `access_count`, `last_access`, `superseded_by`, `stability`, `importance`, `archived`, `scope`) carries every Phase. Embeddings are packed as raw float32 bytes via `array('f', vec).tobytes()` / `array('f', blob).tolist()` so numpy stays out of the hard-dependency set. The schema is idempotent and migratory: `_init_schema` enables WAL + `synchronous=NORMAL` for file-backed stores (so the background consolidator sweeps without blocking reads), sets `cache_size=-64000`, `mmap_size=268435456`, `temp_store=MEMORY`, and `ALTER TABLE ADD COLUMN`s any missing Phase 3/7C/scope columns onto legacy DBs. Indexes include `idx_fact`, `idx_tags`, `idx_memories_lookup (superseded_by, id, timestamp)`, `idx_memories_fact_nocase (fact COLLATE NOCASE, superseded_by, timestamp, id)`, and `idx_memories_scope`. A `memories_fts` FTS5 virtual table (`content='memories'`, `tokenize='unicode61 remove_diacritics 2'`) is kept in sync by three `AFTER INSERT/DELETE/UPDATE` triggers (`memories_fts_aiu/aad/au`) using the FTS5 `'delete'` command for evictions.

The write path (`add(card, scope=None)`, `update(card)` upsert, `delete(memory_id)`, `delete_scope(scope)`, `archive_card(card_id)`, `touch(memory_id, at=None)`, `consolidate_memories(merged_cards, deleted_ids, superseded_ids=None)`) all acquire the lock; `consolidate_memories` wraps its multi-statement apply in `BEGIN IMMEDIATE ... COMMIT` (rollback on exception) so a sweep is atomic. The read path (`get`, `all`, `sql_lookup`, `batch_get`, `count`, `db_size_bytes`) reuses a prepared-statement cache `_stmt_cache` keyed by SQL string. `sql_lookup(field, value)` has an exact-match fast path on `fact` (using `idx_memories_fact_nocase`), a two-phase covering-index substring scan for `fact` (scan `idx_fact` for ids, then `IN(...)` fetch, falling back to a `NOT INDEXED` scan past `_SUBSET_MATCH_LIMIT=900`), a direct LIKE scan for `evidence`, and Python-side JSON tag membership for `tags`.

Vector search is the performance-critical path. `_ensure_vec_cache(np)` lazily builds a `(n_cards, dim)` float32 matrix (SELECT `id, timestamp, embedding, scope ... NOT INDEXED WHERE embedding IS NOT NULL AND superseded_by IS NULL AND archived = 0 ORDER BY timestamp ASC, id ASC`), decodes BLOBs via `np.frombuffer`, and `np.stack`s them; heterogeneous dims latch `_vec_hetero` and fall back to the pure-Python loop. `vector_search(query_vec, k=5, alpha=0.70, scope="default")` runs ONE batched `matrix @ q` matmul (via `native.batch_cosine_similarity`), clips to `[0,1]`, applies a cached per-scope boolean `_scope_mask` (floors out-of-scope rows to `-1.0` before `argpartition`), expands to all rows tied at the k-th boundary, and — when `alpha < 1.0` — batch-loads `last_access`/`stability` and re-ranks by `hybrid_score(cosine, retention, alpha)`. `hybrid_search(query, query_vec, k=5, alpha=0.70, top_n_per_branch=30, scope="default")` is Late Fusion: vector cosine branch + FTS5 BM25 branch, merged by `_rrf_fusion` (Reciprocal Rank Fusion, `Score(d) = α/(60 + r_vec) + (1-α)/(60 + r_bm25) + Boost(d)`, Cormack SIGIR 2009 smoothing constant 60), plus an additive entity-graph boost `0.5 / (1 + 0.001*(N-1)**2)` from `card_edges` that only RE-RANKs cards already surfaced by a branch (never introduces candidates). `_HYDRATION_BUFFER=4` over-fetches from fusion so a transient `delete()` TOCTOU doesn't shrink the returned top-k below k. The decision: one store, one connection, one lock, with numpy/BLAS as an optional zero-copy accelerator and a correct pure-Python fallback for every path.

#### core/decay.py — Ebbinghaus temporal decay

Three pure functions implementing the Phase 7C forgetting curve. `calculate_retention(last_accessed_ts, stability=1.0, current_ts=None, half_life_hours=24.0) -> float` computes `R(t) = exp(-Δt / S)` where `Δt` is `(current_ts - last_accessed_ts)/3600` hours and `effective_half_life = stability * half_life_hours`; it returns `1.0` for never-accessed (`ts <= 0`) or future timestamps, `0.0` for non-positive effective half-life, and clamps to `[0.0, 1.0]`. `update_stability(current_stability, access_count, explicit_importance=0.0) -> float` applies `boost = 1.0 + 0.5*log1p(access_count) + 0.3*explicit_importance` multiplicatively, floored at `1.0` and capped at `10.0`. `hybrid_score(cosine_similarity, retention, alpha=0.70) -> float` fuses `α·cos⁺ + (1-α)·retention`, clamping cosine to `[-1,1]`, flooring negatives to 0, and clamping the result to `[0,1]`. Default `alpha=0.70` gives semantic 70% / recency 30%.

#### core/consolidation.py — off-hot-path housekeeping/merge engine

`Consolidator` runs ONE atomic sweep with three responsibilities. (1) Deduplication: `_find_clusters` uses union-find over pairwise `_are_duplicates` edges (negation guard FIRST via `_are_negations_guard` → `native.are_negations`, then exact case-insensitive fact equality, then `_token_overlap_ratio >= token_overlap_floor` Jaccard, then `_cosine > dedup_threshold` default 0.84); `_merge_cluster` picks the NEWEST survivor when facts differ beyond case/whitespace (a correction wins) but the EARLIEST when facts are token-identical after normalization (canonical first-seen), unions evidence (capped to `_MAX_EVIDENCE_FRAGMENTS=3` via `_merge_evidence`), unions tags, sums `access_count`, takes `MAX(last_access)`, and re-embeds the survivor. Negation pairs (`_NEGATION_MARKERS`: "not", "no longer", "doesn't", ...) NEVER merge. (2) Temporal decay/pruning: `vitality(card, now=None) -> float` computes `S = w_recency*exp(-λ*Δt) + w_access*ln(1+access_count)` (defaults `w_recency=0.7`, `w_access=0.3`, `λ=ln(2)/(30d*86400)`); a card is pruned ONLY if `retention < 0.15` AND `access_count == 0` AND `age >= min_age_seconds=3600` AND `compound_weight == 0.0` — recalled cards are never pruned. (3) Graph summarization: `graph.detect_clusters(min_cluster_size=3, min_edge_weight=0.80)` feeds `_merge_graph_cluster` which selects the highest-centrality survivor. `run() -> ConsolidationReport` snapshots via `store.all()` (lock held only for the read), plans in pure Python (no lock across planning), then applies ONCE via `store.consolidate_memories(survivors, deleted_ids, superseded_ids=superseded_map)` — folded cards are marked SUPERSEDED (audit trail pointer), not hard-deleted. `dry_run() -> dict` plans without committing; `run_async()` offloads via `asyncio.to_thread`; `start_background_loop(interval_seconds=300.0)` runs a daemon thread. `consolidate_memory_space(db_path, retention_threshold=0.15, *, embedder=None)` is the high-level entry point returning a summary dict. The decision: keep the store flat in context size and sub-ms latency regardless of write volume by pushing all O(n²) work off the hot path.

#### core/history.py — time-travel + rollback

`History` owns a sidecar `memories_history` table (`version INTEGER, card_id TEXT, ...all card columns..., seen_at REAL, PRIMARY KEY (card_id, version)`) created lazily on first use against the store's connection. `snapshot(card_id) -> int | None` copies the card's current full state into the log with a per-card-sequential version id and wall-clock `seen_at`; it is called by the client facade BEFORE every mutating op (so the pre-mutation state is recoverable) and returns `None` when the card doesn't yet exist. `versions(card_id) -> list[int]` lists all logged versions ascending; `get_version(card_id, version) -> MemoryCard` reconstructs a card (raises `KeyError` if absent). `rollback(card_id, to_version=None) -> MemoryCard` restores the latest-but-one snapshot (or an explicit version), snapshots the current state first so the rollback is itself undoable, then re-applies via `store.update` (which re-inserts if the row was hard-deleted — resurrection). The design decision: append-only snapshots driven from the client facade rather than trigger-based CDC, because the consolidator and eval-harness seeder write directly to the connection and trigger history would double-log internal mutations interleave with user-driven revisions; only client-mediated revisions are what a user wants to undo. Thread-safe via the store's existing `_lock`.

#### core/mmap_store.py — two-tier file-backed mmap vector store (Method 3)

`MmapVectorStore` replaces the heap-resident `(n, dim)` float32 matrix with a file-backed `np.memmap` written to `embeddings.bin` (contiguous row-major float32, shape `(n, dim)`) plus a sidecar `embeddings.bin.idx` JSON map `{card_id: row_index}`. `build(np)` SELECTs `id, timestamp, embedding, scope ... NOT INDEXED WHERE embedding IS NOT NULL AND superseded_by IS NULL ORDER BY timestamp ASC, id ASC` (the SAME order as the heap path, making the memmap a drop-in), `np.stack`s + `tofile`s, persists the index, and opens `np.memmap(..., mode='r+', shape=(n, dim))`. It raises `_HeteroDim` on mismatched dims so the owning store latches `_vec_hetero` and falls back. `hot_get(card_id, np)` / `hot_warm(card_ids, np)` maintain an `OrderedDict` Hot LRU (default capacity 200, ~0.3 MB heap ceiling) of row COPIES (so cached entries survive page eviction), with move-to-end on access and `popitem(last=False)` eviction. `invalidate()` marks dirty + clears the LRU (called by `MemoryStore._mark_vec_dirty`); `evict_pages_cold()` drops and reopens the mapping read-only to force a cold state (macOS lacks `posix_fadvise`). `resident_matrix_bytes() -> dict` reports honest bounds (`file_bytes`, `hot_lru_bytes`, `hot_capacity_bytes`, `n_rows`, `dim`) rather than fabricating a resident number. The honest finding: the matrix is only ~14.65 MB at 10k cards; ONNX (~360 MB) dominates RSS, so mmap cannot reduce total RSS to 30 MB — the default production path is the ~7%-faster heap BLAS (`use_mmap=False`), with mmap available as an opt-in for cold-start/large-scale probes.

#### core/native.py — pure-Python kernels (BLAS vector + negation heuristic)

A pure-Python kernel module. As of v1.3.0 there is **no Rust extension**: `HAVE_NATIVE` is a constant `False` (kept for API stability — downstream adapters or user code may read it). `batch_cosine_similarity(query_vec, matrix) -> np.ndarray` is the vector path and always uses NumPy/BLAS: `np.asarray(matrix @ query_vec, dtype=np.float32)` calls into platform BLAS (Accelerate on macOS) zero-copy with the GIL released — measured ~9-115x faster than the removed Rust extension's `batch_cosine_similarity_matrix`, which had to clone the matrix into owned `Vec<f32>` to release the GIL because `PyReadonlyArray` is not `Send`. `are_negations(a, b) -> bool` always runs the pure-Python heuristic `_are_negations_py` (a verbatim copy of the v0.1 logic: `_strip_negations` + crude `_stem` + `>= 0.6` Jaccard polarity check). The decision: the shipped wheel is pure-Python and never needs a compiled module. (The removed Rust crate internals are documented as historical record in §5.)

#### core/async_engine.py — asyncio facade

`AsyncMemoryEngine` is a thin awaitable surface over the sync `MemoryStore` for asyncio agents (FastAPI, AutoGen, async LangGraph). Every method delegates via `_run(coro_callable, *args)` → `loop.run_in_executor(None, ...)` onto the default `ThreadPoolExecutor` (capped `min(32, cpu+4)`); it does NOT open a second connection or take a second lock — the store is already `check_same_thread=False` and serializes through its own `_lock`, so a thread-pool worker safely borrows the single held connection, inheriting the store's lock/WAL/mmap guarantees verbatim. It mirrors the store's constructor surface (`add`, `update`, `delete`, `archive_card`, `touch`, `get`, `all`, `count`, `batch_get`, `vector_search`, `hybrid_search`, `consolidate_memories`, `close`), supports `async with` (closes on exit if it owns the store), and exposes `sync_store` as an escape hatch. Construct either with a pre-existing `store` (`_owns_store=False`) or with `**store_kwargs` (creates the store, `_owns_store=True`). The decision: delegation, not reimplementation — the async layer adds no new concurrency semantics, it just makes the sync store awaitable.

#### Core-layer invariants

- One `MemoryStore` connection, one `threading.Lock`: all DB work serializes; external writers sharing the DB file MUST set `PRAGMA busy_timeout` themselves (the store never does).
- `:memory:` DBs stay alive for the store's lifetime via the single held connection.
- Every read path selects the same column order (`_SQL_LOOKUP_SELECT`), so `_row_to_card` produces identical cards regardless of which query ran.
- Live-row filter is universal: `superseded_by IS NULL AND archived = 0` is applied by `all()`, `sql_lookup`, `vector_search`, `hybrid_search` BM25, and `count()`; superseded rows remain retrievable only by direct `get()`.
- Embeddings are packed float32 via `array('f')`; a `None` embedding stores SQL NULL and is skipped by every search path.
- Vector scores are clamped to `[0,1]`; hybrid RRF scores are deliberately NOT clamped (different scale).
- Ordering is deterministic everywhere: `(score desc, timestamp asc, id asc)`.
- `touch()` deliberately does NOT invalidate the vector cache (it changes neither embedding, id, timestamp, nor scope).
- Folded (superseded) cards are never hard-deleted by consolidation; only decay-pruned ids are hard-deleted, and only when `retention < 0.15` AND `access_count == 0` AND past grace AND zero graph centrality.
- v1.3.0 ships a pure-Python wheel — there is no Rust `_native` module to load or miss. `HAVE_NATIVE` is a constant `False`; the vector path is NumPy/BLAS and negation is the pure-Python heuristic.
- FTS5 is optional: if absent, hybrid search degrades to vector-only rather than failing store construction.
- Multi-tier `scope` is enforced on every retrieval path (SQL filter, numpy boolean mask, or iteration-time skip) so out-of-scope cards never surface.

### 4.2 embeddings/ + daemon/ — ONNX, hybrid IPC, shared-memory daemon

The embedding package is the cost-and-correctness center of isotope_zero: it turns text into 384-dim, L2-normalized vectors with zero network calls at inference time and degrades gracefully when onnxruntime/tokenizers are absent.

**`embeddings/__init__.py`** re-exports a single name, `EmbeddingEngine`, from `onnx_embed`. That is the whole public surface of the package at this level — the rest (`embedding_runtime`, `engine`) is reached by explicit import.

**`embeddings/onnx_embed.py` — `EmbeddingEngine`.** The in-process quantized-ONNX embedding engine (Xenova/all-MiniLM-L6-v2, dim 384). Key surface: `embed_text(text) -> list[float]`, `embed_batch(texts) -> list[list[float]]`, `.is_real`, `.dim`. It loads a quantized ONNX model plus a matching tokenizer, caching both on disk under `.isotope_zero_cache`. The forward path is chunked: `_EMBED_CHUNK = 32` caps the peak `token_embeds` tensor at `(32, seq, 384)` fp32 so the 10k scale-seeding sweep never allocates one ~460MB `(10000, seq, 384)` tensor — the tokenizer encodes once per chunk and results are accumulated in input order to preserve the `embed_batch` contract. Design decision: a **deterministic feature-hash fallback** (`_embed_fallback`) produces an L2-normalized blake2b-of-word-tokens + char-trigrams vector into signed buckets of the correct dimension, so identical texts still score cosine 1.0 and unrelated texts ~0 even with no model present. Outputs are L2-normalized so cosine similarity collapses to a plain dot product.

**`embeddings/embedding_runtime.py` — runtime-checkable superset.** A zero-dep-first re-spec of the engine contract. Key types: `Embedder` (a `runtime_checkable` Protocol capturing the duck-typed surface — `embed_text`/`embed_batch`/`is_real`/`dim`), `BaseEmbeddingEngine` (the spec-mandated ABC with abstract `embed_text`/`embed_batch` + async twins + `metadata`), `MRLTruncator` (slices the first `d` dims and re-normalizes via `np.linalg.norm`, zero-copy view + one divide). The runtime must import and be fully testable with ONLY numpy present; `httpx`/`onnxruntime`/`tokenizers` are `try/except ImportError`-guarded and never hard-imported at module top. Design decision: a **deterministic fallback engine** reuses the feature-hash stub pattern from `onnx_embed._embed_fallback` as the terminal safety net and default backend. The Protocol and ABC coexist — the Protocol describes what callers already duck-accept; the ABC is what new concrete engines inherit.

**`embeddings/engine.py` — `HybridEmbeddingEngine`.** The daemon-first embedding engine with silent in-process fallback (Phase 8 synthesis). Constructor: `HybridEmbeddingEngine(model_name="all-MiniLM-L6-v2", socket_path="/tmp/izero.sock", spawn_daemon=True, connect_timeout=10.0, dim=384, cache_dir=".isotope_zero_cache")`. It tries the shared-memory daemon first (via `DaemonClient`); if the socket is unavailable, refused, or a call errors mid-flight, it **transparently and silently** falls back to an in-process local ONNX session (`EmbeddingEngine`). The fallback is deliberately lazy: the in-process engine is constructed only the *first* time the daemon path fails, so onnxruntime stays out of the client process entirely while the daemon is up — a single `log.warning` records the transition, subsequent calls reuse the built engine. `HybridEmbeddingEngine` is a **duck-typed drop-in** for both `DaemonClient` and `EmbeddingEngine` (`.embed_text`, `.embed_batch`, `.is_real`, `.dim`) and is accepted anywhere either is — `MemoryStore`, `QueryRouter`, `Consolidator`, `IsotopeZero`. Active mode is one of `"daemon" | "in_process" | "fallback_pseudo"`, set once during `__init__` and again only on a daemon failure.

**`daemon/` — shared-memory embedding daemon (Phase 7A).** `daemon/__init__.py` intentionally imports NOTHING. Importing `isotope_zero.daemon` is a no-op so a client's RSS story (~360MB of onnxruntime shared library) is preserved even if a stray `import isotope_zero.daemon` is added.

`daemon/server.py — IzeroDaemon`: the ONNX process — loads one `EmbeddingEngine` (the onnxruntime-heavy object) and serves embedding requests over a Unix domain socket (`/tmp/izero.sock` by default). It MAY import onnxruntime/numpy and MUST NOT import `isotope_zero.daemon.client`. Wire protocol: every client→daemon message is `struct.pack(">II", len(header_json), len(payload)) + header_json + payload`; every daemon→client reply is `struct.pack(">I", len(reply_json)) + reply_json`. Commands: `ping`, `hello` (returns `is_real`/`dim`/`model`), `embed_batch` (header carries a client-named POSIX shared-memory segment `shm`/`n`/`dim`/`seq`; the daemon attaches, writes `n*dim` float32 results row-major zero-copy through the page cache, replies `{"ok":true,"n":n,"dim":dim,"seq":seq}`), `stats`, `shutdown` (unlinks the socket and `os._exit(0)`). `_embed_lock` serializes engine calls because the tokenizer is not thread-safe; `_MAX_HEADER_LEN` is 4MiB and `_MAX_PAYLOAD_LEN` 1GiB cap malformed peers. The daemon self-exits after `--idle-timeout` (default 300s) idle or on SIGTERM/SIGINT. Large batches move **zero-copy through POSIX shared memory** (`multiprocessing.shared_memory`) rather than over the socket.

`daemon/client.py — DaemonClient`: stdlib-only RPC client and duck-typed drop-in for `EmbeddingEngine`. HARD REQUIREMENT: no third-party imports at module level — no onnxruntime, no tokenizers, no numpy — so importing it in a client process does not load onnxruntime. Constructor: `DaemonClient(model_name="all-MiniLM-L6-v2", socket_path="/tmp/izero.sock", spawn=True, ...)`; exposes `.embed_text`, `.embed_batch`, `.is_real`, `.dim` (default 384). Key methods: `_connect`/`_try_connect`/`_spawn_daemon` (may spawn the daemon subprocess if `spawn=True` and no socket), `_poll_connect`, `_send_cmd`, `_recv_exact`, `_embed_batch_once`, plus `ping`/`stats`/`close`/`shutdown`. Vectors travel over POSIX shared memory. Its stdlib-only import discipline is what makes the 360MB isolation real.

#### The vector guarantee

**Always returns a vector, never raises for transport failure.** `HybridEmbeddingEngine` tries the daemon first; if the `/tmp/izero.sock` socket is missing, refused, or a call errors mid-flight, it silently falls back to an in-process `EmbeddingEngine`; if onnxruntime is itself absent, the `EmbeddingEngine` feature-hash fallback still returns a deterministic L2-normalized 384-dim vector. A single `log.warning` records the daemon→in-process transition; no caller ever sees an exception for a transport fault.

### 4.3 retrieval/ + engine/ + graph/ — hybrid search, adaptive dispatch, knowledge graph

**`retrieval/hybrid_search.py` — `QueryRouter`.** The read-path brain — decides HOW to answer a query (SQL vs vector) and truncates results by token budget. Key class: `QueryRouter(store: MemoryStore, embedder: EmbeddingEngine)` with `.query(query, token_budget=300) -> QueryResult`. Three paths: (1) **SQL path** — for explicit state lookups ("what's my current project?", "who am I?") matched by `_SQL_ROUTE_PATTERNS` regexes, a cheap indexed SQL lookup with zero embedding cost; (2) **Vector path** — embeds the query once and runs top-k cosine scan only when SQL can't confidently answer; (3) **Budget-aware retrieval** — `_apply_budget` ranks candidates by marginal value per token and truncates when `token_budget` is reached OR marginal value drops below the running average (diminishing-returns halt). A **lexical exact-match boost** runs after the vector top-N pass and before `_apply_budget`: MiniLM collapses numeric tokens ("port is 2204" vs "2203" embed to cosine ~0.99), so query-token (especially numeric/identifier) verbatim hits get a capped `score = vector_score + boost`, with a second-stage "numeric-commitment" disambiguation for tight clusters of near-duplicate facts. The router also computes `tokens_saved_vs_raw` (raw full-history replay vs what isotope_zero injected) and records access on survivors only so the temporal-decay scorer can distinguish vital (recalled) cards from cold (never-recalled) ones.

**`engine/adaptive_search.py` — scale-adaptive dispatcher.** Since v1.3.0 the shipped wheel carries **no native kernel** — `self._kernel` is `None` for every install — so the dispatcher routes **every N to the zero-copy NumPy/BLAS path** (the numpy int8 oracle is NOT used; it is slower than BLAS at every scale). The int8-quantized + float32 buffer set and the hysteresis thresholds (`INT8_THRESHOLD=2000`, `BLAS_THRESHOLD=3000`) are retained as research substrate for a future shipped kernel. The int8 NEON kernel (`isotope_zero._native.simd_int8_batch_dot`) was prototype-only (`prototypes/simd_int8_v0.5`) and never compiled into a shipped wheel; its measured crossover (NEON wins below ~2-3k cards, BLAS wins above) is a record of the prototype, not the shipped behavior. Zero-alloc framing: the BLAS path writes into a pre-allocated `_scores` buffer via `np.dot(..., out=_scores)` (truly zero-alloc in the dot-product hot path). A per-instance `threading.RLock` serializes compute (guaranteeing no corruption, not parallel reads).

**`graph/relation_graph.py` — semantic knowledge graph (Phase 7C).** Transforms flat memory cards into a dynamic weighted graph of semantic edges to boost recall and surface consolidation candidates. Pure stdlib (sqlite3, math, time, `collections.deque`); operates on the store's `sqlite3.Connection` (does not create its own); no threading. Schema: `card_edges(source_id, target_id, relation_type DEFAULT 'semantic', weight, created_at)` with `idx_card_edges_source`/`_target`. Key functions: `init_graph(conn)` (idempotent DDL), `insert_edge(conn, src, tgt, relation_type='semantic', weight=1.0)` (UPSERT, weight = MAX old vs new), `_cosine_similarity`/`_jaccard` helpers, `auto_link_cards(conn, card_id, tags, embedding, all_embeddings, cosine_threshold=0.75)` — creates `"semantic"` edges where cosine > threshold (weight=cosine) and `"shared_tag"` edges where Jaccard > 0 (weight=jaccard), skipping self-edges. `get_neighbors(conn, card_id, min_weight, relation_types)` returns outgoing edges sorted by weight desc; `compound_weight` sums outgoing weights as a centrality/hub measure; `detect_clusters(conn, min_cluster_size=3, min_edge_weight=0.80)` runs undirected BFS over edges ≥ min_edge_weight and returns connected components of size ≥ min_cluster_size; `prune_stale_edges(conn, max_age_seconds=7*86400)` deletes old edges. High-density, decay-stable clusters are candidates for consolidation into summary cards, and the graph provides neighbor expansion that boosts recall beyond a single top-k cosine scan.

### 4.4 extraction/ + eval/ — write-path triage, benchmarks, adversarial harness

**`extraction/fact_extractor.py`.** The first stop on the write path — classify user intent (ADD/UPDATE/DELETE) and compress raw input into cards, stdlib-only. Key signals: `DELETE_PATTERNS` ("forget", "remove", "stop remembering" — strict, pure removal), `UPDATE_PATTERNS` ("actually", "i no longer", "switched to"), `ADD_PATTERNS` ("my name is", "i prefer"). Scoring weights: `_BASE_SIGNAL_WEIGHT=0.65`, `_EXTRA_SIGNAL_WEIGHT=0.12`, `_MAX_CONFIDENCE=0.95`, `_ESCALATE_THRESHOLD=0.6`, `_DEFAULT_ADD_SCORE=0.35`. Key functions: `classify_action` (fast keyword classifier), `_extract_target_id`/`_normalize_id` (slug-ish stable id), `_mock_llm_re_examine` (a **deterministic stand-in** for a future local-LLM triage call — NOT a real API, re-examines with looser rules: negation → DELETE-leaning, past-tense "was X now Y" → UPDATE), `compress_to_card`. `compress_to_card` is **conservative by design** — it never invents facts unsupported by a verbatim substring of the input (`evidence`); in doubt it keeps the fact slightly long rather than risk a lossy rewrite.

**`extraction/prompts.py`.** **Reserved namespace, not on the shipped path.** The v1.0 write path (`classify_action`/`compress_to_card`) is fully deterministic — stdlib regex + the mocked re-examination. This module reserves the `prompts` namespace for the planned local-LLM escalation interface (Ollama/llama.cpp) so the extraction package layout matches the documented distribution tree; the shipped heuristics remain the default and an LLM path would be an opt-in escalation tier on top of them.

**`eval/benchmark.py`.** Phase 0 harness measuring the cost thesis directly. Produces a Markdown table of tokens-per-useful-fact (isotope_zero vs raw-context-history), latency per operation (write/read/vector-search ms), estimated cost savings (`$0` local embeddings vs OpenAI text-embedding-3-small at `$0.02/1M` tokens), and a 100%-recall correctness floor on structured fact queries. Runs a synthetic multi-turn session (identity, preferences, project, corrections) followed by explicit (must hit SQL) and fuzzy queries. Measures reality against a remote-embedding dollar baseline.

**`eval/adversarial.py`.** Adversarial stress + competitor-benchmark harness across four commercial memory failure modes. Dataclasses: `ScaleResult` (Section A: 10k+ cards, vector/SQL p50/p99 latency + RSS), plus sections B–D. Section B: needle-in-a-haystack + distractor floor (LongMemEval-style recall %). Section C: negation/polarity bombardment (zero incorrect merges under contradictory pairs). Section D: maximum concurrency + DB contention warfare (concurrent worker processes, background consolidation, zero `OperationalError`/corruption). It wires the full stack — `HybridEmbeddingEngine`, `QueryRouter`, `Consolidator`, `IsotopeZero`, `relation_graph` (`init_graph`/`auto_link_cards`/`detect_clusters`/`get_graph_stats`). Design principle, stated verbatim: **measure reality, never fabricate a passing threshold** — each `claim_*` field is recorded beside the measured value so a claim that does not hold renders FAIL, not a silent relax.

### 4.5 cli/ — debug, render, menu, dashboard, _fmtutil

**`cli/debug.py` — the `izero` dispatcher.** The pure-stdlib argparse entry point exposing every CLI subcommand and the `--json` machine contract. Subcommands: `inspect` (verbose diagnostic store report — count, DB size, embedding mode, avg embedding dim, top-N lowest-vitality decay candidates, token footprint; `--json`), `dry-run-consolidation` (previews `Consolidator.dry_run()` without committing), `add <fact>` (`--evidence`/`--tags`/`--scope`/`--id` upserts via `client.remember`), `active` (warmest memories by vitality DESC; `--top`/`--tags`/`--min-vitality`), `recall <query>` (`--k`/`--alpha`), `search <query>` (hybrid vector+BM25+graph), `list` (`--tags`/`--limit`, newest-first), `get <id>`, `forget <id>` (`--yes` skips confirm), `touch <id>`, `tags` (tag distribution), `stats` (count/size/mode/tokens/tags/vitality histogram), `dashboard` (`--db`/`--interval`/`--once`), `hook <event>` (Claude Code lifecycle hook entrypoint reading JSON from stdin, dispatching to `integrations.run_hook`; events: `session_start|user_prompt|file_read|block_memory_write|bash_output|stop|pre_compact`), and `plugin install` (`--target`/`--editor claude|cursor|codex`/`--dry-run`; local-path copy into the editor config dir, no marketplace, rewrites `.mcp.json`). Every command has two output paths — `--json` is the stable machine contract (source of truth for scripts/SDK/MCP) and the human path delegates to `render.py`. The diagnostic commands (`inspect`, `dry-run-consolidation`) keep their dense banner-style format and are carved out of the clean-output redesign. `_open_client` is built with `spawn_daemon=False, use_mmap=False` so the CLI never starts the shared-memory daemon or mmaps a vector index — the engine still embeds (real ONNX if available, else deterministic fallback). Default DB is `~/.isotope_zero/isotope_zero.db` if it exists, else `:memory:`; a missing explicit `--db` is reported gracefully for reads, and `add` creates it. A bare `izero` (no subcommand) lazily imports `cli.menu.run_menu`; `plugin install` and `hook` are dispatched before `_resolve_db_path` because their subparsers declare no `--db`.

**`cli/render.py`, `_fmtutil.py`, `menu.py`, `dashboard.py` — the human surface.** `render.py` owns the human-readable path: pure formatters returning `str` (no I/O), giving the CLI a Mem0-style voice where the fact text is the hero and ids/scores/vitality floats/token counts live behind `--verbose`. Functions `format_hits`/`format_list_rows`/`format_card`/`format_add`/`format_forget`/`format_touch`/`format_tags`/`format_stats` are trivially testable. `_glyph()` falls back from Unicode (`✓`/`·`/`→`) to ASCII (`ok`/`-`/`->`) on non-UTF-8 stdout. `_fmtutil.py` is the stdlib-only shared helper module (`human_bytes`, `age_days`, `trunc`, `_SECS_PER_DAY`) that lets `render.py` import display helpers without pulling the engine stack into its import graph. `menu.py` is the bare-`izero` interactive onboarding menu — a welcome banner plus a navigable command list that invents no store logic, calling existing `_cmd_*` helpers with prompted args. Two transports: `rich` (arrow-key navigation via `rich.live.Live` alternate-screen, lazy-imported) and plain (numbered `1) add … 0) exit`). `dashboard.py` is the live read-only TUI: `run_dashboard(db_path, interval=2.0, once=False)` renders one panel (cards/size/mode, fixed-width vitality bar `█▒░`, recent adds, decay candidates, reclaimable tokens) refreshing until Ctrl-C. Two transports: `rich` (smooth `Live` + screen restore) and plain (`\033[2J\033[H` clear-and-reprint). `--once` prints one static frame and exits 0 — scriptable and the deterministic test path. It reuses the `inspect`/`stats`/`dry-run` data paths, invents no queries, and uses a strict `create=False` missing-DB guard.

### 4.6 mcp/ + client.py + integrations/ — the integration surfaces

**`src/isotope_zero/client.py` — the unified `IsotopeZero` facade.** The Phase 8 synthesis object that hides the `MemoryStore`, `HybridEmbeddingEngine`, `History`, and (lazily) `Consolidator` behind four verbs — `remember`, `recall`, `touch`, `consolidate`. `IsotopeZero` (aliased as `IsotopeClient`, the v1.0 SDK name) is a facade, not a reimplementation: it wires the winning subsystem stack together and inherits the store's WAL, lock, mmap vector index, and atomic consolidation transaction verbatim. Construction is cheap for `:memory:`; `db_path="path.db"` opens/creates a file and enables WAL. Defaults make `IsotopeZero()` immediately useful: in-memory SQLite, the hybrid embedder with `spawn_daemon=True` (transparently falling back to in-process or deterministic pseudo-embeddings), mmap-backed vector index, `alpha=0.70` cosine-vs-Ebbinghaus-retention fusion. The constructor also takes `model_name="all-MiniLM-L6-v2"`, `socket_path="/tmp/izero.sock"`, `use_mmap=True`, and `ttl_seconds=None`.

The write path is `remember(fact, evidence="", tags=None, importance=0.0, ttl_seconds=None, scope=None, card_id=None) -> str`. The engine embeds the *fact* before the card enters the store, so the vector index and graph auto-linking see a fully-formed card. `remember` upserts via `store.update` (ON CONFLICT DO UPDATE), so re-remembering an existing id overwrites in place — but first it snapshots the prior state into `client.history` so the revision is undoable via `client.history.rollback`. TTL is encoded as a `ttl:<seconds>` tag (no schema change); `recall`/`search` filter expired cards client-side and `consolidate` hard-prunes them. `prune_expired()` scans and deletes all TTL-expired cards.

The read path is `recall(query, k=5, alpha=None) -> list[dict]`, returning `{id, fact, evidence, score, tags, timestamp}` sorted by score desc — the raw 384-float embedding is deliberately stripped so it never bloats agent context. `final = alpha*cosine + (1-alpha)*retention`; `alpha=1.0` is pure cosine. When a TTL default is active, `recall` over-fetches by `_TTL_OVERFETCH=8` so post-filter still yields up to k live hits. `search(...)` is the hybrid late-fusion path: semantic vector + BM25 (FTS5) + entity-graph boost, delegating to `store.hybrid_search`. `scoped(user_id, agent_id, run_id)` is a context manager that stamps a deterministic scope onto writes and masks out-of-scope rows on reads; nested scopes replace (inner wins). `touch(card_id)` bumps access_count and reinforces Ebbinghaus stability. `consolidate()` lazily imports `Consolidator`, prunes TTL-expired cards first, then runs one full dedup/decay/graph sweep, returning `{merged, pruned, survivors, tokens_before/after/reclaimed, latency_ms, pruned_mean_retention}`. `count()` returns live card count; `close()` (atexit-registered) drops the engine's daemon socket.

**`src/isotope_zero/mcp/server.py` — the MCP stdio server.** `IsotopeZeroServer` + `build_mcp_app` expose the memory store over the Model Context Protocol so any MCP-compatible agent client can read/write local memory with no knowledge of the internals. `IsotopeZeroServer.__init__(db_path=None, embedder=None, use_daemon=False)` wires a `MemoryStore` + `QueryRouter` + `EmbeddingEngine` (or `DaemonClient` when `use_daemon=True`) into one testable object — tests instantiate `IsotopeZeroServer(db_path=":memory:")` and call methods directly. The default DB is file-backed in `.isotope_zero_cache/` (or `$ISOTOPE_ZERO_DB`) so memory persists across restarts. `build_mcp_app(server=None, use_daemon=False)` locates the MCP server class across SDK versions (`MCPServer` for mcp 2.x, `FastMCP` for 1.x) and registers five `@app.tool()` handlers: `add_memory(content, tags=None)` (runs `classify_action` ADD/UPDATE/DELETE, `compress_to_card`, embeds the compressed fact, merges provenance tags, persists), `query_memory(query, token_budget=300)` (SQL-first/vector-second within a budget, returns `tokens_saved_vs_raw`), `delete_memory(memory_id)`, `get_metrics()` (DB size, card count, embedding mode, cumulative tokens saved), and `run_consolidation()` (one `Consolidator.run()` sweep). `main()` runs the app over stdio (the default MCP transport).

The full `integrations/` package — the editor-integration plugin with lifecycle hooks, skills, and manifests for Claude Code / Cursor / Codex — is detailed in §7.

#### CLI/MCP guarantees

- The CLI never starts a daemon — `_open_client` in `cli/debug.py` passes `spawn_daemon=False` to `IsotopeZero`.
- The CLI never mmaps — `_open_client` passes `use_mmap=False`, so no file-backed `np.memmap` vector index is opened.
- Falls back to pseudo-embeddings — the `HybridEmbeddingEngine` transparently degrades to deterministic pseudo-embeddings when no ONNX runtime is present, so `recall`/`search` work with zero optional deps (degraded semantic quality, ranked results still returned).

### 4.7 types.py + tokens.py + diagnostics.py (rust_bridge/ removed in v1.3.0)

**`types.py` — the shared integration contract.** One module that every subsystem (embeddings, triage, store, router, mcp, eval) imports so parallel-built modules slot together without reconciliation. It defines the canonical data shapes: `MemoryCard` (a compressed memory unit — a `fact` plus minimal `evidence`, never the full raw input), `ActionType`/`ActionResult` (write-path triage decision with a `[0.0,1.0]` `confidence` validated in `__post_init__`), `QueryHit`/`QueryResult` (budget-aware retrieval results carrying `tokens_saved_vs_raw`), and `ConsolidationReport` (sweep outcome with `merged_cards`/`decayed_cards`/`tokens_reclaimed`). `MemoryCard` carries the full life-cycle state: access tracking (`access_count`, `last_access`), the Phase 3 supersession audit trail (`superseded_by`), Phase 7C Ebbinghaus fields (`stability` default `1.0`, `importance`, `archived`), and multi-tier scoping (`scope` default `"default"`). `now_ts() -> float` wraps `time.time()` so tests and the benchmark can monkeypatch determinism without touching `time.time` globally. The decision: freeze one dataclass contract and let every subsystem depend on it, so modules can be built and tested in parallel.

**`tokens.py` — the single source of truth for token math.** Cost is isotope_zero's first-class metric, so every module must use the same estimator. `estimate_tokens(text: str) -> int` avoids a real tokenizer dependency on the hot path: a tight regex `_TOKEN_RE = re.compile(r"\S+|\s+")` splits on word/whitespace runs, then blends a run-count estimate with a char-based `len(text)//4` rule of thumb, averaging the two for stability across short and long inputs. The blend `max(1, (len(runs) + char_estimate) // 2)` keeps latency sub-millisecond and approximates GPT-style BPE within ~5% for English; the eval harness cross-checks against a real `tokenizers` model when present. The invariant: every token-counting call site in the codebase routes through this one function.

**`diagnostics.py` — structured-ish logging config.** A small idempotent logging configurator controlled by `ISOTOPE_ZERO_LOG_LEVEL` (with `IZERO_LOG_LEVEL` as a fallback alias), defaulting to `WARNING`. `configure_logging() -> str` installs one `StreamHandler(sys.stderr)` on the `"isotope_zero"` logger namespace with a compact `%(asctime)s %(levelname)-7s %(name)s: %(message)s` formatter, `propagate=False` to avoid double-prints, and replaces prior handlers on reconfigure so a level change takes effect cleanly. It returns the effective level name and is a no-op when re-called with the same env value. Writing to stderr (never stdout) is load-bearing: MCP uses stdout for stdio transport, so any stdout logging would corrupt the protocol. `get_level() -> str` reports the current level. One idempotent entrypoint called from every CLI/MCP/smoke-test entry, keeping normal runs quiet and fast while DEBUG exposes per-operation records from `core.store`, `core.consolidation`, etc.

**`rust_bridge/` — REMOVED in v1.3.0.** The PyO3 native-extension package directory (`src/isotope_zero/rust_bridge/`, compiled by maturin into `isotope_zero._native`) was **deleted in v1.3.0** — the shipped wheel is pure-Python and contains no `.so`/`.pyd`/`.dylib`. The removed crate's internals (Cargo.toml, `src/lib.rs`, `src/vector.rs`, `src/negation.rs`) are documented as historical record in §5.

> **v1.3.0 superseding marker — REMOVED.** This section is a historical record
> of the Rust native core that shipped through v1.2.x. In **v1.3.0 the crate**
> (`src/isotope_zero/rust_bridge/`, module `isotope_zero._native`) **was
> REMOVED** and the wheel is **pure-Python**: `HAVE_NATIVE` is a constant
> `False`, `batch_cosine_similarity()` runs NumPy/BLAS, `are_negations()` runs

The Rust native core is an **optional accelerator** — never a hard dependency. When the `.so`/`.pyd`/`.dylib` cannot build or load, the NumPy fallback in `core/native.py` (`HAVE_NATIVE=False`, described in §4.1) keeps the package fully runnable. The bridge's invariant: a missing, half-built, or ABI-mismatched native module can never break import or change behavior, and negation behavior is bit-identical whether or not native loads.

**`Cargo.toml`** names the crate `isotope_core` v1.1.1, `crate-type=["cdylib"]`, with `pyo3 0.21` (`abi3-py310` stable ABI + `extension-module`), `rayon 1.8` for data parallelism, and `numpy 0.21` for zero-copy matrix reads; release profile is `opt-level=3`, `lto="thin"`, `codegen-units=1`. The crate declares `extension-module` and uses abi3 (`PYO3_NO_PYTHON=1` on Linux) so one wheel serves CPython 3.10/3.11/3.12.

**`src/lib.rs`** exposes three `#[pyfunction]`s matching the module name `_native`: `batch_cosine_similarity(query, matrix_flat, dim)` (Vec-based fallback, releases GIL), `batch_cosine_similarity_matrix(query, matrix)` (zero-copy numpy fast path — reads `(n,dim)` float32 directly from the numpy buffer, copies into owned Rust slices, releases GIL around the SIMD batch), and `are_negations(a, b)`.

**`src/vector.rs`** is the dot core: on `aarch64` explicit NEON with 4 independent 128-bit FMA accumulators (16 floats/iteration, 384 = 24 full iterations, 4-wide FMA tail + scalar epilogue); other targets rely on rustc auto-vectorization (AVX2/AVX-512); rayon parallelizes over rows above `PAR_MIN_ELEMENTS = 1<<18`. The decisive finding from the Phase 6 smart-bridge prototype: `PyReadonlyArray` borrows Python memory and is not `Send`, so releasing the GIL forces Rust to clone the entire 10k×384 matrix (~15 MB) before computing; NumPy's zero-copy `matrix @ q` releases the GIL around the platform BLAS C kernel (Accelerate) and was measured ~9–115× faster. So the vector dot-product hot path stays on BLAS (`core/native.py:batch_cosine_similarity`), while the Rust `batch_cosine_similarity_matrix` remains available but is not the shipped default.

**`src/negation.rs`** is a bit-for-bit port of `consolidation._are_negations` (lowercased, space-padded marker removal longest-first matching the Python tuple order, whitespace collapse, `ing/ed/es/s` stemmer, ≥0.6 Jaccard gate) because the correctness budget allows zero incorrect merges. This is the one Rust kernel that ships on the hot path: `core/native.py:are_negations` calls `_native.are_negations` when `HAVE_NATIVE` and transparently falls back to the pure-Python `_are_negations_py` on any native failure.

The native kernel is loaded by `_try_import_native_kernel` in `engine/adaptive_search.py` — `isotope_zero._native.simd_int8_batch_dot` if the `.so` is on disk. The numpy int8 path is the correctness oracle used when the `.so` is absent.

## 6. Prototypes — the 11-phase research arc (v0.1 → v1.0)

Each prototype phase tested a hypothesis and was judged by measured numbers. The arc's throughline: six acceleration hypotheses were tested honestly, three were refuted (hybrid pre-filtering, mmap, binary POPCNT), two were partial/conditional wins (quantization, native SIMD), one was the structural-RSS daemon — and the capstone shipped exactly the layers that survived measurement.

### Phase 1 — python_v0.1 (v0.1.0, frozen reference baseline)

The frozen pure-Python reference implementation: SQLite store, hybrid SQL/vector router, local ONNX embeddings, consolidation, MCP server, and CLI — a 129-test-green milestone (5 skipped behind `IZERO_STRESS=1`). Cut from the repo root via `git mv`, so full commit history is preserved and it stays runnable at any time. Captured-at-freeze results: 100% needle recall at 500 distractors, 99.3% context compression (1,200 → 9 cards), vector-search p99 0.43 ms at 10k cards, SQL-lookup p99 ~0.07 ms, and RSS 195 MB at 1k cards (~370–410 MB at 10k — the honest structural floor). This is the yardstick every later prototype measures itself against; most were scaffolded directly from it.

### Phase 2 — rust_v0.2 (v0.2.0a1, frozen reference — Phase 6 "Smart Bridge")

A frozen reference that places each workload on its empirically-fastest path, chosen from measured benchmarks rather than assumption. The decisive finding: the Rust vector path was **rejected**. `PyReadonlyArray` borrows Python memory and is not `Send`, so releasing the GIL forces Rust to clone the entire 10k×384 matrix (~15 MB) before computing; NumPy's zero-copy `matrix @ q` releases the GIL around the platform BLAS C kernel (Accelerate) and was measured ~9–115× faster. So vector dot-product stays on BLAS, while negation/polarity detection — which has no BLAS equivalent — moves to a bit-for-bit Rust PyO3 port (`_native.are_negations`) with a clean pure-Python fallback. Verified at freeze: vector p99 0.30 ms (PASS), negation 0/100 incorrect merges (PASS), SQL p99 0.66 ms (PASS), 100% recall, 0/0 concurrency errors; RSS 394 MB FAILs as structural (ONNX MiniLM ~135 MB + the float32 matrix). This prototype contributed the shipped negation kernel and the durable "BLAS wins the vector hot path" decision that every later phase inherits.

### Phase 3 — hybrid_v0.3 (v0.3.0a1, scaffolded from python_v0.1 — Method 1, REFUTED)

Method 1, Hybrid Pre-Filtering: SQLite FTS5 BM25 lexical candidate extraction (≤50 cards) followed by NumPy vector re-rank, betting on sub-0.05 ms latency at 10k. **Both claims FAIL by large margins.** Hybrid p99 measured 0.87–0.93 ms — *slower* than the 0.33–0.52 ms full-matrix BLAS scan it was meant to beat, because at this scale the baseline is already a single BLAS matmul (~0.3 ms), so FTS5 parse + candidate retrieval + re-rank adds overhead that exceeds the scan it replaces. Worse, needle recall collapsed to 40%: the semantic-phrased needle queries share no rare token with their target, and the dense distractor set steals BM25 rank. This committed negative taught the arc that BLAS is genuinely fast and that lexical pre-filtering cannot preserve semantic recall without the router's boost/truncation logic.

### Phase 4 — quantization_v0.4 (v0.4.0a1, scaffolded from python_v0.1 — Method 2, PARTIAL WIN)

Method 2, Int8 scalar quantization (SQ8): each 384-dim embedding shrinks from float32 (1,536 B) to int8 + a per-vector scale (4× / 75% reduction). **Two targets PASS cleanly:** footprint 3.66 MB vs 14.65 MB at 10k (4× smaller, under the <4.0 MB claim), and Spearman rank correlation 0.99997–1.0000 vs float32 cosine (top-k order preserved, scores within ~0.001). **Latency is the honest negative the thesis anticipated:** int8 is 5–8× slower (p99 2.55–3.21 ms vs 0.40–0.47 ms), because numpy's `@` on int8 arrays is not BLAS-accelerated (BLAS kernels are float32/float64 only) and upcasts to a generic int32 loop. As a pure-Python/numpy prototype, Method 2 is a partial win: the accuracy/memory claims hold, the latency win does not — and it points squarely at the gap a native SIMD kernel could close.

### Phase 5 — simd_int8_v0.5 (v0.5.0a1, scaffolded from quantization_v0.4 — Method 4, CONDITIONAL WIN)

Method 4 closes the gap Method 2 flagged by computing the int8 dot-product in a native Rust PyO3 kernel using hardware int8 instructions: NEON `sdot` on aarch64 (the live M4 path), AVX-VNNI-INT8 on x86_64 (compile-guarded; the README documents the signed-vs-unsigned `_mm256_dpbssd_epi32` trap). Footprint and rank correlation PASS unchanged from Method 2. The latency target is a **conditional win**: the raw NEON kernel measured 0.357 ms p99 at 10k (~3.6× off the <0.10 ms target, ~2.2× slower than BLAS) — but it **beats BLAS below ~3k cards** (0.011 ms vs 0.064 ms at 500; 0.042 vs 0.061 at 2k) and meets <0.10 ms at n≤4k, i.e. exactly the realistic local-agent-memory scale. The clean 10k sweep didn't materialize because true `vdotq_s32` is gated behind unstable `stdarch_neon_dotprod` (tracking #117224) and won't compile on stable Rust 1.97; the kernel falls back to a `vmull+vpaddlq` widening idiom and per-call `Vec` copies. This prototype contributed the native int8 kernel and the measured scale-crossover that later dispatch logic is built on.

### Phase 6 — mmap_v0.6 (v0.6.0a1, scaffolded from rust_v0.2 — Method 3, REFUTED)

Method 3, two-tier file-backed `np.memmap` storage with a Hot RAM LRU (N=200), betting it bounds process RSS under 30 MB. **The thesis premise is factually wrong, confirmed by measurement.** At 10k cards the float32 matrix is only 14.65 MB; the ~394 MB RSS is dominated by the ONNX runtime (~360 MB), not the matrix. mmap cannot subtract the matrix from an RSS it doesn't own — RSS *rose* ~40 MB (memmap mapping overhead on top of unchanged ONNX). The backend is production-safe (bit-identical results, clean invalidation, graceful fallback) and the cold-page-fault penalty was nullified by the macOS unified buffer cache (cold p99 0.29 ms = hot 0.29 ms), but it provides no measured benefit at prototype scale and the LRU only starts mattering past ~1M cards. This refutation pinned the structural RSS wall and is why the shipped product defaults mmap off.

### Phase 7 — daemon_v0.7 (v0.7.0a1, Phase 7A — shared-memory embedding daemon, 3/5)

Phase 7A moves the heavy onnxruntime engine out of every client and into one daemon process, with POSIX shared-memory handoff (batch vectors written row-major into a client-named `shared_memory` segment, never streamed over the socket) and a duck-typed stdlib-only `DaemonClient`. **3/5 claims hold.** Client RSS < 10 MB FAILs structurally (275 MB peak — python+numpy+sqlite3+the 10k-card store is the real floor; only the ~360 MB onnxruntime share is removed). The 5-worker amortization PASSes decisively (402 MB total vs 776 MB in-process — the daemon amortizes ONNX across the fleet). IPC latency FAILs honestly: the 0.05 ms target is pure socket dispatch (measured 0.017 ms ping RTT), but the claim's own unit is a warm `embed_text` round-trip, which includes ~1.1 ms ONNX inference on the hot path either way and matches in-process p99. Recall parity PASSes bit-exactly (max |Δvec| = 0.00, top-k 100% match). This contributed the daemon, the shared-memory protocol, and the auto-spawn/`--idle-timeout 0` harness fix.

### Phase 8 — binary_popcnt_v0.8 (v0.8.0a1, Phase 7B — 1-bit binary POPCNT, 1/4)

Phase 7B adds a 2-stage pipeline: 1-bit sign quantization (`>=0`→1) packed to uint8 (48 B/card), XOR+POPCNT Hamming over all cards to select candidates, then float32 BLAS re-rank. **Only 1/4 claims hold.** Footprint PASSes (4.80 MB at 100k, 32× / 96.9% reduction). POPCNT Hamming p99 FAILs (2.462 ms vs <0.05) — Stage 1 must O(n)-scan every packed row. The pipeline p99 (2.838 ms) is essentially identical to direct float32 BLAS (2.832 ms), so Stage 2's 0.141 ms re-rank cannot compensate. Recall@10 is **0%**: sign-bit thresholding of off-the-shelf ONNX MiniLM embeddings discards too much signal — the Hamming ordering is orthogonal to the cosine ordering, none of the float32 top-10 appear in the POPCNT candidate pool. This committed negative taught that binary quantization requires embedding-aware training or product-quantization codebooks, not pre-trained float32.

### Phase 9 — decay_graph_v0.9 (v0.9.0a1, Phase 7C — scaffolded from daemon_v0.7 — Ebbinghaus decay + graph consolidation, 2/3)

Phase 7C transforms the engine into a temporally-aware cognitive memory: card insertion auto-links (cosine > 0.75 or shared tags) into a SQLite `card_edges` graph; retrieval fuses 70% cosine + 30% Ebbinghaus retention `R(t)`; a periodic consolidator dedups cosine clusters, prunes stale isolated memories (R(t)<0.15, compound_weight==0, access_count==0 → archive), and merges tight graph clusters (N≥3, edge weight >0.80) into summary survivors. **2/3 claims hold:** temporal recall 100% (fresh "I moved to NYC" correctly suppresses stale "I live in SF"); storage reduction 89% (300 → 33 active cards, 8.1× index shrink); latency overhead 0.070 ms FAILs narrowly (1.4× the 0.05 ms target, from per-result `now_ts()` + retention math). This contributed `decay.py`, `graph.py`, the alpha-weighted `vector_search`, and the consolidation sweep that ships in the capstone.

### Phase 10 — adaptive_dispatch_v1.1 (scale-adaptive search dispatch)

A design exercise that operationalizes the v0.5 crossover finding: one dispatcher holds both an int8-quantized and a float32 copy of the matrix in a pre-allocated buffer set and routes each query to whichever kernel is faster at the *current* active count, with hysteresis (int8 at N≤2000, BLAS at N>3000, latched path between). The BLAS path writes into a pre-allocated `_scores` buffer (`np.dot(..., out=...)`) for zero allocation in the dot-product hot path; the native int8 path cannot accept an `out=` buffer (its PyO3 signature returns a fresh array), so it allocates one (n,) array per call — strictly better than the synthesis_v1.0 baseline, but not literally zero-alloc on the native path. The numpy int8 fallback is kept deliberately as a correctness oracle (slower at every scale, expected). This prototype contributed the scale-adaptive routing idea and the pre-allocated-buffer discipline that the capstone's search path inherits.

### Phase 11 — synthesis_v1.0 (v1.0.0a1, Phase 8 — Grand Synthesis capstone, 4/4)

The capstone unifies the winning stack behind one facade, `isotope_zero.client.IsotopeZero` (`remember` / `recall` / `touch` / `consolidate`). A new `HybridEmbeddingEngine` is daemon-first with a **silent** in-process ONNX fallback that never raises on transport failure. The shipped layers: the Phase 7A shared-memory daemon (centralizes the ~360 MB onnxruntime), the Phase 7C Ebbinghaus decay + semantic graph (`recall` fuses cosine + retention at α=0.70), and the Phase 5 mmap zero-copy index — **opt-in and OFF by default**. The honest reason mmap is off: grafted onto the concurrency-hardened store, it **SIGILL-crashed (exit 132)** under 10-thread stress because `vector_search` runs the `matrix @ q` matmul outside `_ensure_vec_cache`'s lock, so a concurrent `add()` → `invalidate()` tears down the live memmap view mid-matmul. Combined with Phase 5's finding (matrix only ~15 MB, heap BLAS ~7% faster, mmap raised RSS +40 MB), defaulting it off is the defensible call. **Grand Synthesis: 4/4 claims hold** — parity 100% (top-k id+order across two independent instances), temporal recall 100%, storage reduction 98.5% (5,518 → 83 tokens, 199 merged), and facade overhead 0.03 ms (median-of-5-rounds p99, isolated by canceling the shared embedding cost).

## 7. Integrations — the izero-plugin (Claude Code / Cursor / Codex)

### Local-first editor integration (v1.2.0)

The v1.2.0 editor integration mirrors mem0's *capture surface* — Claude Code lifecycle hooks, slash-command skills, editor plugin manifests — but routes every capture pipe into the **local** `IsotopeZeroServer` / SQLite store at `~/.isotope_zero/isotope_zero.db` instead of `mcp.mem0.ai`. No network, no API key, works offline: that is the headline differentiator, and it is enforced at import time.

### Single-entrypoint design: `izero hook <event>`

The linchpin is ONE shared CLI subcommand, `izero hook <event>`. Every bash hook wrapper in `integrations/izero-plugin/hooks/<event>.sh` is a 3-line script that reads its stdin JSON and pipes it to this entrypoint. All logic lives in the testable Python module `isotope_zero.integrations.hooks`, which exposes two functions: `run_hook(event, db_path)` — the stdin-driven CLI entrypoint — and `handle_hook(event, payload, db_path)` — the pure `(payload, db_path) -> dict` core that tests call directly with canned JSON, no live editor needed. `run_hook` reads stdin, resolves `db_path` from `$ISOTOPE_ZERO_DB` then `~/.isotope_zero/isotope_zero.db`, dispatches via the `_HANDLERS` table, prints the result JSON to stdout, and exits 0 (or 2 for the write-guard block).

This inverts mem0's anti-pattern: mem0 ships ~15 separate Python scripts under `scripts/`, each with its own `sys.path.insert`, identity resolution, and `urllib.request.urlopen` to `api.mem0.ai`. izero collapses all of these into one dispatch table with trivial bash wrappers, so the hooks are unit-testable (feed canned JSON, assert the emitted JSON) and memory stays on the local store. Unknown events are a no-op (exit 0) so a forward-compatible editor payload never breaks a hook.

### The 7 lifecycle hooks and what each emits

`SUPPORTED_EVENTS` is exactly `("session_start", "user_prompt", "file_read", "block_memory_write", "bash_output", "stop", "pre_compact")`. Each handler returns the Claude Code hook-output shape: `{"hookSpecificOutput": {"hookEventName": ..., "additionalContext": "...", "permissionDecision": "allow"|"deny", "permissionDecisionReason": "..."}}`, built by the `_context`/`_allow`/`_deny` helpers. A `deny` returns exit code 2 (the Claude Code block signal); all others return 0.

- **`file_read`** (PreToolUse:Read) — the flagship. Injects a prior-work timeline scoped to the file being read. Path-scoped recall via `store.sql_lookup("tags", "file:<rel>")` (exact single-tag membership, no schema change) plus a semantic fallback via `query_memory(rel, token_budget=150)`. Gated on `_FILE_READ_MIN_BYTES = 1500` so tiny files skip the round-trip. De-duped by card id; emits `izero: prior work on <rel>` + up to 8 `• <fact>` lines. Always allows.
- **`bash_output`** (PostToolUse:Bash) — gated auto-capture. Scans `tool_response` against `_TRACEBACK_RE` (Traceback/panic/FATAL/Error/Exception/RuntimeError/...). Skips git noise via `_GIT_NOISE_RE` (`git commit|merge|rebase|cherry-pick|stash`). On a real error, it dedups by `_error_signature` (sha1 of `command[:80]::error_line[:120]`): if the signature already exists, it calls `store.touch` on the first match (boosting vitality so the recurring error surfaces higher) and never duplicates; if new, it writes a `type:anti_pattern` card tagged `error:<sig>`, `source:bash_output`, `file:<rel>` per traceback file, and `branch:<branch>`. Bounded by `_BASH_ERROR_CAP_LIMIT = 3` and consolidation dedup. Emits `allow` + a `"/izero:recall ..."` prior-fix rubric.
- **`user_prompt`** (UserPromptSubmit) — injects top relevant memories for the prompt via `query_memory(prompt, token_budget=200)`, up to 5 hits. Skips prompts under 20 chars.
- **`session_start`** (SessionStart) — injects a one-line store summary: `<count> memories · <size> · onnx|local embeddings · (branch <name>)` plus a `/izero:recall` hint. Returns None on an empty store.
- **`block_memory_write`** (PreToolUse:Write|Edit|MultiEdit) — the write-guard. Pure permission gate, no store call. Denies direct writes to the store file and SQLite sidecars, redirecting to the `add_memory` MCP tool. **The only hook that propagates the python exit code** (exit 2 to deny) — its wrapper `block_memory_write.sh` forwards `$?` verbatim rather than swallowing it; all other wrappers `|| true` and exit 0. A missing entrypoint fails open (allow) so a broken izero install never wedges the editor.
- **`stop`** (Stop) and **`pre_compact`** (PreCompact) — local-heuristic session summary capture, tagged `session` / `pre-compaction` respectively (plus `source:<prefix>` and `branch:<branch>`).

### Local heuristic session summary (no LLM, no network)

mem0's Stop/PreCompact handlers call a cloud LLM summarizer. izero's cannot, so `_summarize_session_locally(payload, db_path, tag_prefix=...)` extracts decisions from the transcript with no LLM. It reads the transcript from `transcript_path` (a JSONL file) or inline `transcript`/`session`, then `_extract_decision_signals` runs a regex over signal phrases (`decided|decision|always use|never use|prefer|preference|doesn't work|don't try|rule of thumb|convention is|standard is|agreed|conclusion`), keeping lines 15–300 chars. Each surviving signal is compressed via `isotope_zero.extraction.fact_extractor.compress_to_card` (local ADD/UPDATE/DELETE triage, no LLM), embedded with `server.embedder.embed_text`, and stored. Writes are bounded to 5 signals per session. If the transcript is absent or under 100 chars, or no signals fire, it returns None — no card. The time-window fallback (cards touched in `[session_start, now]`) is a future enhancement gated on the Stop/PreCompact payload spec.

### The 6 skills

The bundle ships six `skills/*/SKILL.md` files, surfaced as `/izero:*` slash commands that call the local MCP tools:

- **`/izero:remember <fact>`** — stores via `add_memory`, classifying one `type:` tag (`type:decision`/`type:anti_pattern`/`type:user_preference`) from signal words and stamping `source:remember`. Returns `memory_id`, `action` (ADD/UPDATE), `confidence`, `fact`, `tags`.
- **`/izero:recall <query>`** — `query_memory(query, token_budget=300)`; the store routes SQL-first for explicit tag/fact/evidence lookups and falls back to vector similarity. Presents hits fact-first, citing `[izero:<id>]`, with `route_used` and `tokens_saved_vs_raw`.
- **`/izero:peek <query|id>`** — `query_memory(query, token_budget=100)`. Detects a bare hex/UUID id (`^[a-f0-9-]+$`) for direct lookup; compact one-liners, no inline `evidence`.
- **`/izero:forget <id>`** — `delete_memory(memory_id)`. Destructive: confirms first, deletes only by explicit id (never by guessed query); returns `{"memory_id", "deleted"}`.
- **`/izero:stats`** — `get_metrics()`; reports `db_size_bytes`/`db_size_human`, `card_count`, `embedding_is_real` (false = deterministic pseudo-embedding fallback), `cumulative_tokens_saved_vs_raw`, `cumulative_raw_history_tokens`.
- **`/izero:decay-review`** — `get_metrics` pre-sweep, then `run_consolidation` (atomic WAL transaction, safe alongside active reads/writes). Reports `merged_cards`, `decayed_cards`, `survivors`, `tokens_before`/`tokens_after`/`tokens_reclaimed`, `latency_ms`, `pruned_mean_vitality`.

### The write-guard (store file + SQLite sidecars, exact; `~/.isotope_zero` prefix)

`_protected_store_paths(db_path)` returns `(protected_files, protected_dir_roots)`. `protected_files` matches the store DB path **exactly** plus its SQLite sidecar variants (`-wal`/`-shm`/`-journal` and the legacy `.wal`/`.shm`/`.journal`) — so a legitimate sibling file next to a relocated store stays writable. `protected_dir_roots` prefix-matches the conventional `~/.isotope_zero` dir (guards the default location even when `db_path` points elsewhere) plus the DB's parent **only when that parent looks store-dedicated** (basename contains `isotope_zero` or `.izero`) — an incidental scratch dir where the DB happens to live is NOT guarded. The whole DB parent dir is deliberately not prefix-matched. A `:memory:` store returns `({}, {})` — nothing on disk to protect.

### stdio MCP config (izero-mcp, no url, no api key)

`.mcp.json`, `.cursor-mcp.json`, and `.codex-mcp.json` are identical: `{"mcpServers": {"izero": {"command": "izero-mcp", "args": [], "env": {"ISOTOPE_ZERO_DB": "~/.isotope_zero/isotope_zero.db"}}}}`. There is no `url`, no `Authorization`, no `api_key` field anywhere — the anti-cloud headline made literal. The `izero-mcp` stdio server is launched in-process; the `ISOTOPE_ZERO_DB` env is shared with the hook entrypoint so the MCP server and hooks read/write one store. Per-editor `plugin.json` variants wire the bundle to each host: `.claude-plugin/plugin.json` sets `contextFileName: AGENTS.md` and a non-sensitive `userConfig.db_path`; `.cursor-plugin/plugin.json` points `skills`/`hooks`/`mcpServers` at `./skills/`, `./hooks/cursor-hooks.json`, `.cursor-mcp.json`; `.codex-plugin/plugin.json` adds an `interface` block (displayName, `capabilities: [Read, Write]`, `brandColor: #10B981`, defaultPrompts). The three hook-maps differ only in root var (`${CLAUDE_PLUGIN_ROOT}` vs `${CURSOR_PLUGIN_ROOT}` vs `${PLUGIN_ROOT}`), matcher spelling (`SessionStart` vs `sessionStart`), and Cursor/Codex adding `startup|resume|compact` matchers and timeouts.

### `izero plugin install` helper

`plugin_install(target, editor, dry_run)` resolves the bundle from the dev repo path (`<repo>/integrations/izero-plugin/`, via `parents[3]`) or, for a PyPI install, by walking `importlib.resources.files("isotope_zero").parents` for a sibling `integrations/izero-plugin/`. It picks the target dir from per-editor defaults (claude→`~/.claude/plugins/izero`, cursor→`~/.cursor/plugins/izero`, codex→`~/.codex/plugins/izero`) unless `--target` overrides. The MCP command resolves to `izero-mcp` when `shutil.which` finds it (clean, no args), else `sys.executable` (or `python3`) with `-m isotope_zero.mcp.server` — never a URL or key. `--dry-run` validates that present manifests (`plugin.json`, `.mcp.json`, `hooks.json`) parse as JSON and prints the plan without writing. The real install does an idempotent `shutil.copytree(dirs_exist_ok=True)`, then rewrites **all three** MCP configs (`.mcp.json`, `.cursor-mcp.json`, `.codex-mcp.json`) so `mcpServers.izero.{command,args,env.ISOTOPE_ZERO_DB}` match the resolved command — skipping the editor variants would strand Cursor/Codex pointing at a nonexistent console script. Sibling servers/keys are preserved; the write is atomic (temp file + `os.replace`). Marketplace/remote discovery is deferred to v1.3.0; this helper is strictly a local-path installer.

### Offline guarantee

Zero network imports in `src/isotope_zero/integrations/`: `grep -rnE '^\s*(import|from)\s+(requests|urllib|httpx|aiohttp|openai|http)'` returns nothing. The only hits for `http`/`requests`/`urllib`/`api_key`/`openai` are docstrings and comments explaining their *absence* (e.g. the hooks.py docstring describing mem0's `urllib.request.urlopen` anti-pattern, and the README privacy section). The integrations module imports only stdlib (`json`, `os`, `re`, `sys`, `logging`, `hashlib`, `subprocess`, `shutil`, `pathlib`, `importlib.resources`); the lazy `IsotopeZeroServer` seam falls back to deterministic pseudo-embeddings when onnxruntime is absent, so hooks work with zero optional deps. No `url`, no `Authorization`, no `api_key` in any manifest. Memory persists at `~/.isotope_zero/` and is never transmitted.

## 8. Adapters — LangChain / LlamaIndex / AutoGen / CrewAI

`izero-adapters` (version 0.1.0, MIT, zero hard dependencies) bridges Isotope Zero's SQLite + float32 BLAS vector engine into the standard `VectorStore` / `Memory` interfaces expected by LangChain, LlamaIndex, AutoGen, and CrewAI. Every adapter routes through one shared seam — `izero_adapters._engine.Engine`, a framework-agnostic facade over the real `MemoryStore` + an embedder — so no adapter touches SQLite, the schema, or the embedding model directly. The engine is located by path (`prototypes/synthesis_v1.0`, overridable via `IZERO_ENGINE_PATH`) and is not pip-installed. Embedder selection degrades gracefully: an explicit `embedder=` → the shared-memory daemon (`use_daemon=True`, if reachable) → local ONNX `EmbeddingEngine` (if `onnxruntime` + `tokenizers` import) → a deterministic, L2-normalized feature-hash stub (always available, zero deps). `DEFAULT_MODEL = "all-MiniLM-L6-v2"`, `DEFAULT_DIM = 384`. Each framework submodule imports its framework lazily and guarded, so `import izero_adapters.<framework>` never fails when the framework is absent; duck-typed shims keep each class constructible and testable with nothing installed. All engine results are plain dicts (`{id, text, score, metadata, tags, timestamp}`), and free-form metadata round-trips through the store as `key=value` tag pairs.

**LangChain** (`langchain.py`): `IsotopeZeroVectorStore` subclasses `langchain_core.vectorstores.VectorStore` when `langchain_core` is importable, else a duck-typed `_BaseVectorStore` shim. It implements `add_texts`, `add_documents`, `similarity_search`, `similarity_search_with_score`, `similarity_search_by_vector`, `delete`, and the `from_texts` classmethod. LangChain's `embedding` argument is accepted for signature parity but ignored — Isotope Zero manages its own vectors. A `filter` dict post-filters results by metadata equality (the LangChain convention). A second class, `IsotopeChatMessageHistory`, subclasses `langchain_core.chat_history.BaseChatMessageHistory` (the real ABC when installed), storing each turn as a card tagged `chat_history` with `session_id` in metadata; it exposes sync `messages` / `add_messages` / `clear` plus async `aadd_messages` / `aget_messages` / `aclear`.

**LlamaIndex** (`llamaindex.py`): `IsotopeZeroVectorStore` subclasses `llama_index.core.vector_stores.types.BasePydanticVectorStore` when installed, with `stores_text = True`. It implements `add([BaseNode])` (reads `get_content()` / `.text`, `.metadata`, `.id_`, and passes through a node-carried `embedding` when present), `query(VectorStoreQuery)` → `VectorStoreQueryResult` (`.nodes` / `.similarities` / `.ids`), `delete(ref_doc_id)`, and a no-op `persist`. The LlamaIndex-parity bridge maps `query.filter` keys `scope` / `user_id` / `doc_id` (plain dict or `MetadataFilters`) onto the engine's native scoping axis.

**AutoGen** (`autogen.py`): `IsotopeZeroMemory` is a standalone object — AutoGen's memory model is not a strict base-class contract — exposing `.remember` / `.recall` / `.forget` / `.clear_session` / `.count`. Per-agent isolation comes from a session tag derived as `agent:{agent_id}` (or an explicit `session_tag`); `recall(filter_session=True)` (the default) post-filters to that tag, while `filter_session=False` searches globally. `attach_to_agent` wires into a `ConversableAgent` by registering a context-injection hook via `register_reply("auto", ...)` that recalls relevant memories into the system message and remembers the latest user turn; it raises a clean `RuntimeError` when `pyautogen` is absent.

**CrewAI** (`crewai.py`): `IsotopeZeroMemory` is likewise standalone, with the same uniform API plus `recall_for_agent` and `attach_to_crew`. Session tags compose hierarchically: `crew:{crew_id}:agent:{agent_id}` when both given, `crew:{crew_id}` or `agent:{agent_id}` when only one, none for global memory. `recall_for_agent(agent_id, query)` builds a teammate's tag on the fly for cross-agent recall within the same crew without exposing other crews. `attach_to_crew` first tries `crew.memory = self`, then falls back to registering `before` / `after` task hooks that recall into task context and remember task outputs.

## 9. The npm launcher

The `npm/` package (`isotope-zero`, version 1.1.1, MIT, Node ≥ 18) is a thin global launcher that lets JS-first environments and CI install and run the `izero` CLI via `npm i -g isotope-zero` without managing a Python environment. It ships no real logic — all behavior lives in the Python package. `bin/izero.js` resolves a Python interpreter via `lib/ensure-env.js`'s `resolvePython(pkgVersion)`, then `spawn`s `python -m isotope_zero.cli.debug` with `stdio: "inherit"` and passes argv verbatim, so help, progress, and exit codes are identical to the Python console script. The resolution order is uv-first with graceful degradation: (1) reuse an existing `~/.izero/venv` that already imports `isotope-zero==<pkgVer>` (the durable home — uv may be absent this run); (2) `uv` on PATH or bootstrapped into `~/.izero/bin` → build/refresh the dedicated venv with the version pinned to the npm package version; (3) system `python3` + `pip install --user`; (4) no Python → an actionable `ENOPython` error. The npm version and the pinned PyPI version are kept in lockstep (`npm i -g isotope-zero@1.1.1` installs `isotope-zero==1.1.1`); a `.installed-version` stamp at `~/.izero/.installed-version` makes warm starts instant. A `mkdir`-based build lock serializes concurrent invocations so parallel `izero` subprocesses don't both fall through to system pip. Launcher-private flags are `--izero-`-prefixed to avoid collisions with the Python CLI: `--izero-version` / `-V`, `doctor` (diagnostics + self-test import), and `--izero-self-test`. A `node --test` suite in `test/launcher.test.mjs` covers the version flag, doctor, arg passthrough, and the no-Python error path.

## 10. Tooling — benchmarks, tools/, docs/, meta-docs

### Build system (setuptools + pure-Python)

Since v1.3.0 Isotope Zero is built with **setuptools** (`setuptools>=68` + `wheel` in the `[build-system]` of `pyproject.toml`) and produces a single **universal `py3-none-any` wheel** — there is no Rust extension, no maturin, no cibuildwheel. `setup.py` exists for ONE job the declarative `[tool.setuptools.data-files]` table cannot do: ship the repo-root `integrations/izero-plugin/` tree at the wheel root with its subdirectory structure intact (`hooks/`, `skills/<name>/`, `.claude-plugin/`, etc. — pyproject data-files globs flatten `hooks`/`skills` and break the build). The pure-Python package lives under `src/isotope_zero/`. `MANIFEST.in` keeps the `LICENSE`, `README.md`, `CHANGELOG.md`, and the `integrations/izero-plugin/**/*` bundle in the sdist so `izero plugin install` works from an sdist install. The historical maturin/PyO3/abi3 build (through v1.2.x) is documented as record in §5 and the prototype READMEs.

### Console scripts

`[project.scripts]` installs three entry points: `izero = "isotope_zero.cli.debug:main"` (the main read-only inspector / dashboard CLI), `izero-mcp = "isotope_zero.mcp.server:main"` (the Model Context Protocol server), and `izero-benchmark = "isotope_zero.eval.benchmark:main"` (the eval/latency harness). A separate thin **npm launcher** (§9) provisions an isolated Python venv on `postinstall` and proxies argv/stdio/signals to the Python `izero` CLI; it carries no native binaries and is platform-independent.

### Optional-dependency extras

The runtime has a single hard dependency — `numpy>=1.24.0` (the float32 BLAS path and int8 quantizer; `sqlite3` is stdlib and deliberately not listed). Everything else is an extra in `[project.optional-dependencies]`: `onnx` (in-process local ONNX embeddings, `$0 inference`), `ollama` and `openai` (`httpx>=0.24.0` transports for local-LLM / OpenAI-compatible remote embedding endpoints), `mcp` (`mcp>=1.0.0`), `fallback` (`tokenizers>=0.15` + `pydantic>=2.6` for the deterministic pure-Python write path when ONNX is unavailable), `dashboard` (`rich>=13.0` for the smooth TUI refresh; absent it degrades to a stdlib clear-and-reprint loop), `all` (aggregator of every runtime), `adapters` (`langchain-core`, `llama-index-core`, `pyautogen`, `crewai` runtimes for the separately-installed `adapters/izero_adapters` SDK package), and `dev` (`pytest`, `pytest-asyncio`, `hypothesis`, `psutil`, plus `onnxruntime`+`tokenizers` so the ~10 real-embedding tests pass without a second install).

### CI matrix (`ci.yml`)

The `CI` workflow (`.github/workflows/ci.yml`) runs on `push: [main]` and all pull requests. The `test` job is a `fail-fast: false` matrix of **three OSes × three Pythons**: `ubuntu-latest`, `macos-14`, `windows-latest` × `3.10/3.11/3.12`. It runs a plain `pip install -e ".[dev]"` (setuptools editable install — no Rust toolchain, no maturin build step since v1.3.0), then `pytest src/tests/ -q -m "not perf"`. The wall-clock perf markers (`test_hybrid_search::TestHybridPerf`, the 5ms p99 SLA) are **excluded** from the shared-runner matrix as noise on contended hosts. A separate `stress` job (`ubuntu-latest`, Python 3.12, `continue-on-error: true` so it never blocks PRs) installs `".[dev,onnx]"`, sets `IZERO_STRESS=1`, and runs the 10k-card extreme-stress + perf budgets (vector p99 ≤ 250ms, sql p99 ≤ 1ms, hybrid p99 ≤ 5ms, RSS ≤ 4GB).

### Tools and Docs Tree

`tools/izero_cli/` is a standalone, read-only inspection + maintenance CLI (console script `izero`) decoupled from `prototypes/`. It opens databases in URI read-only mode (`file:<path>?mode=ro`, `uri=True`) with `PRAGMA query_only=ON` as a second line of defense, so its ten inspection commands (`inspect`, `search`, `card`, `daemon-status`, `watch`, `doctor`, `diff`, `export`, `benchmark`, `stats`) never mutate a live store; only `import` and `vacuum` use explicit read-write connections. ### Release pipeline (`release.yml`, `release-npm.yml`)

There are **two release workflows**, both triggered by `push: tags: v*` and deliberately kept in separate files so an npm failure never blocks the PyPI/GitHub path. Since v1.3.0 `release.yml` has three jobs: a single `build` job (ubuntu, `python -m build --outdir dist`) that produces the sdist + one **universal `py3-none-any` wheel** — no cibuildwheel, no per-OS/per-abi matrix, no Rust cross-compile targets — a `publish` job, and a `smoke-pypi` job. The build job's verify step asserts the wheel contains **no `.so`/`.pyd`/`.dylib` and no `rust_bridge/` artifact** (the regression guard for the v1.3.0 removal). The `publish` job runs in the `pypi` environment with job-scoped `id-token: write` + `contents: write`, downloads the artifacts, and uses `pypa/gh-action-pypi-publish@v1.14.2` (pinned tag, not the floating `release/v1` branch) with **OIDC trusted publishing** as the default (no long-lived secret); `secrets.PYPI_API_TOKEN` is an optional fallback, and `skip-existing: true` makes re-runs idempotent. `softprops/action-gh-release@v2` then creates the GitHub Release with `generate_release_notes: true` and attaches `dist/*`. `smoke-pypi` (3-OS matrix, Python 3.12) pip-installs the *just-published* wheel and asserts `import isotope_zero` + `__version__ == tag` (no native extension to import since v1.3.0). `release-npm.yml` publishes the `isotope-zero` npm launcher to npmjs.com from `npm/` with Node 24, `npm publish --provenance --access public` (Sigstore provenance via `id-token: write`), gated on `secrets.NPM_TOKEN`.

## 12. How it differs from mem0 (the comparative audit, distilled)

The `MEM0_COMPARATIVE_AUDIT.md` opens with an eight-dimension matrix. The load-bearing differences:

**1. Cold start (~100× faster).** isotope_zero's cold-start RSS is 23.1 MB (the interpreter + numpy floor); mem0's stack pulls in a full API client + graph DB driver + hosted embedding service. The audit measures isotope_zero cold start ~100× lighter than mem0's.

**2. Retrieval latency (~165–665× faster).** isotope_zero's vector p99 at 10k cards is 0.284 ms — a single BLAS matmul into platform Accelerate. mem0 routes every query over HTTPS to a remote embedding endpoint + hosted vector DB, so latency is network-bound (tens to hundreds of milliseconds). The audit puts the gap at ~165–665× depending on network conditions.

**3. Dependency weight (~30× lighter).** isotope_zero's hard dependency set is exactly `numpy>=1.24.0`; `sqlite3` is stdlib. mem0 carries API clients, graph DB drivers, and a cloud SDK. The audit measures the dependency footprint ~30× smaller.

**4. Network deps (zero vs mandatory).** isotope_zero has zero network imports in its integrations module — enforced at import time by grep. mem0's hooks ship ~15 separate Python scripts, each with `urllib.request.urlopen` to `api.mem0.ai`. This is the structural headline: isotope_zero works fully offline; mem0 cannot function without its cloud.

**5. Fact reconciliation (tie).** Both detect negation/supersession. mem0 uses an LLM-mediated V3 additive extraction schema; isotope_zero uses a deterministic rule-based triage (`classify_action` ADD/UPDATE/DELETE + `_are_negations` Jaccard gate) with a reserved `prompts.py` namespace for future local-LLM escalation. The audit calls this a tie in capability, with isotope_zero's approach being deterministic and offline.

**6. Graph flexibility (mem0 wins).** mem0's graph store supports richer multi-hop relational queries. isotope_zero's `relation_graph.py` is a weighted semantic-edge graph tuned for consolidation candidate detection and neighbor-expansion recall boosting — deliberately simpler.

**7. Multi-tenancy maturity (mem0 wins).** mem0's multi-tenant cloud architecture is production-mature. isotope_zero's multi-tier scoping (`scope` column + per-query masks + adapter session tags) provides isolation but is not a multi-tenant SaaS platform.

**8. Novel cognitive model (isotope_zero's moat).** isotope_zero's Ebbinghaus temporal decay (`R(t) = exp(-Δt/S)`, stability reinforcement on recall) and off-hot-path consolidation (dedup + decay-prune + graph-cluster merge) have no mem0 equivalent. mem0 stores facts; isotope_zero models forgetting.

**Patterns adapted from mem0.** The audit's Section 2 catalogs mem0 code patterns isotope_zero re-implemented deterministically: V3 additive extraction → rule-based `classify_action` + negation detection; multi-tier scoping → a SQLite `scope` column; MD5 dedup → content-aware hashing with union-find clustering; hybrid retrieval → FTS5 BM25 + entity-graph boost + Reciprocal Rank Fusion. The principle: take the structural ideas, drop the cloud, make them deterministic and local.

**Use-case fit.** isotope_zero for edge / offline / low-latency / single-binary deploy / cost-sensitive workloads. mem0 for multi-tenant SaaS / cloud workflows / teams that want managed infrastructure. They are not competitors in the same deployment envelope.

## 13. Glossary

- **MemoryCard** — the compressed memory unit: a `fact` plus minimal `evidence` (never the full raw input), a 384-dim float32 embedding, access tracking (`access_count`, `last_access`), Ebbinghaus fields (`stability`, `importance`, `archived`), supersession pointer (`superseded_by`), and `scope`. Defined in `types.py`; persisted as one row in the `memories` SQLite table.

- **Ebbinghaus retention** — the forgetting curve `R(t) = exp(-Δt / S)` where `Δt` is hours since last access and `S = stability * half_life_hours` (default 24h). Implemented in `core/decay.py`. A card's retention decays toward 0 unless reinforced by recall (`touch` bumps `access_count`, which `update_stability` uses to boost `stability`).

- **hybrid_score** — the fusion function `α·cos⁺ + (1-α)·retention` (default `alpha=0.70` → 70% semantic / 30% recency). Cosine is clamped to `[-1,1]`, negatives floored to 0, result clamped to `[0,1]`.

- **RRF (Reciprocal Rank Fusion)** — the late-fusion formula `Score(d) = α/(60 + r_vec) + (1-α)/(60 + r_bm25) + Boost(d)` merging the vector cosine branch and the FTS5 BM25 branch. Cormack SIGIR 2009 smoothing constant 60. The entity-graph boost `0.5 / (1 + 0.001*(N-1)**2)` only re-ranks cards already surfaced by a branch.

- **BLAS** — Basic Linear Algebra Subprograms. The `matrix @ q` matmul in `vector_search` calls into platform BLAS (Accelerate on macOS) zero-copy with the GIL released. Measured ~9–115× faster than the Rust-era PyO3 vector path (removed in v1.3.0), which had to clone the matrix to release the GIL.

- **ONNX** — Open Neural Network Exchange. isotope_zero uses a quantized ONNX Xenova/all-MiniLM-L6-v2 model (dim 384) for in-process embeddings. `_EMBED_CHUNK = 32` caps the peak tensor at `(32, seq, 384)` fp32.

- **FTS5** — SQLite's full-text search virtual table. `memories_fts` (`content='memories'`, `tokenize='unicode61 remove_diacritics 2'`) provides the BM25 lexical branch of hybrid search. Kept in sync by three AFTER INSERT/DELETE/UPDATE triggers. Optional: if absent, hybrid search degrades to vector-only.

- **scope** — multi-tier scoping axis (default `"default"`). Enforced on every retrieval path (SQL filter, numpy boolean mask, or iteration-time skip) so out-of-scope cards never surface. Set via `IsotopeZero.scoped(user_id, agent_id, run_id)` or adapter session tags.

- **supersession** — the audit-trail pointer `superseded_by`. When consolidation folds a card into a survivor, the folded card is marked SUPERSEDED (not hard-deleted). Superseded rows are excluded by the universal live-row filter (`superseded_by IS NULL AND archived = 0`) but remain retrievable by direct `get()`.

- **consolidation** — the off-hot-path sweep with three responsibilities: deduplication (union-find over pairwise duplicate edges, negation-guarded), temporal decay/pruning (hard-delete only when `retention < 0.15` AND `access_count == 0` AND past grace AND zero graph centrality), and graph-cluster merge (N≥3, edge weight >0.80 → highest-centrality survivor). Runs atomically via `store.consolidate_memories` in `BEGIN IMMEDIATE ... COMMIT`.

- **vitality** — the consolidator's liveness score `S = w_recency*exp(-λ*Δt) + w_access*ln(1+access_count)` (defaults `w_recency=0.7`, `w_access=0.3`, `λ=ln(2)/(30d*86400)`). Used to rank decay candidates and decide pruning.

- **daemon (Phase 7A)** — `IzeroDaemon`, a process owning one `EmbeddingEngine` (~360 MB onnxruntime) and serving embedding requests over a Unix domain socket (`/tmp/izero.sock`). Large batches move zero-copy through POSIX shared memory. Self-exits after `--idle-timeout` (default 300s).

- **HybridEmbeddingEngine** — the daemon-first embedding engine with silent in-process fallback. Tries the daemon; on any transport fault, transparently falls back to in-process `EmbeddingEngine`; if onnxruntime is absent, the feature-hash fallback still returns a deterministic 384-dim vector. Never raises for transport failure. Active mode: `"daemon" | "in_process" | "fallback_pseudo"`.

- **HAVE_NATIVE** — a constant `False` in `core/native.py`, kept for API stability since v1.3.0 (downstream adapters or user code may read it). The Rust `isotope_zero._native` extension no longer exists; negation always runs the pure-Python heuristic and the vector path is NumPy/BLAS.

- **adaptive dispatch** — `engine/adaptive_search.py`'s scale-adaptive dispatcher. Since v1.3.0 no native kernel ships (`self._kernel` is `None` for every install), so every N routes to the zero-copy NumPy/BLAS path. The int8-quantized buffers and the hysteresis thresholds (`INT8_THRESHOLD=2000`, `BLAS_THRESHOLD=3000`) are retained as research substrate for a future shipped kernel; the int8 NEON kernel itself was prototype-only (`prototypes/simd_int8_v0.5`).

- **tokens_saved_vs_raw** — the first-class cost metric: tokens that raw full-history replay would have injected vs what isotope_zero actually injected, tracked on every query by `QueryRouter`.

- **`izero`** — the main CLI console script (`isotope_zero.cli.debug:main`). 12 subcommands. The npm launcher (`npm i -g isotope-zero`) proxies to this.

- **`izero-mcp`** — the MCP stdio server console script (`isotope_zero.mcp.server:main`). Exposes five tools: `add_memory`, `query_memory`, `delete_memory`, `get_metrics`, `run_consolidation`.

- **izero-plugin** — the editor-integration bundle (v1.2.0): 7 lifecycle hooks, 6 slash-command skills, and per-editor manifests (`.mcp.json`/`.cursor-mcp.json`/`.codex-mcp.json` + `plugin.json` variants) for Claude Code / Cursor / Codex. All local-path, no marketplace, no network.

- **setuptools** — the build backend (`setuptools>=68` + `wheel` in `pyproject.toml` `[build-system]`) since v1.3.0. Produces one universal `py3-none-any` wheel — pure-Python, no compiled extension; `setup.py` ships the `integrations/izero-plugin/` data tree at the wheel root. (The historical maturin/PyO3 backend, through v1.2.x, compiled the Rust extension into `isotope_zero._native`.)
